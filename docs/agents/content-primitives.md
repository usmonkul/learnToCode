# Content primitives

Reached from AGENTS.md when writing lesson or challenge prose that needs more than plain semantic HTML. Prose itself needs no component: lesson files write plain `<p>`, `<h2>`, `<ul>`, `<strong>`, `<blockquote>`, and `LessonPage` wraps the rendered lesson in `@tailwindcss/typography`'s `.prose` class for free. Reach for a primitive only for what HTML alone can't do — and use these exact contracts, don't invent new props.

All live in `src/components/content/`.

| Component | Props | Notes |
|---|---|---|
| `CodeBlock` | `lang` (string, e.g. `"python"`), `children` (a template-string code sample) | Static, syntax-highlighted, has a copy button. Never make this editable/runnable — live code execution is explicitly out of scope. |
| `Callout` | `type` (`"tip"` \| `"note"` \| `"warning"` \| `"danger"`), `title` (optional), `children` | Colored box with an icon per type. |
| `Quiz` | `question`, `options` (string array, **no duplicates within one Quiz** — array items double as React keys), `correctIndex`, `explanation` | Local `useState` only. Progress tracking is scoped to lesson completion (see `docs/agents/auth-and-progress.md`) — don't wire individual quiz answers to Supabase or any other persistence. |
| `Exercise` | `title` (defaults to `"Mashq"`), `children` | Prompt box; typically wraps a `<Solution>`. |
| `Solution` | `children` | Collapsible "Yechimni ko'rsatish", built on `ui/Disclosure`. |
| `KeyPoints` | `children` (`<li>` elements) | Bulleted summary box, usually at a lesson's end. |
| `Figure` | `src`, `alt` (defaults to `''`, but always pass a real one), `caption` (optional) | Image + caption. |
| `SqlPlayground` | `schema` (SQL string: `CREATE TABLE`/`INSERT` statements that seed a fresh in-memory SQLite database on mount), `initialQuery` (optional starter query), plus optional `challenge`/`topicId`/`slug`/`nextChallenge` to opt into grading | One of three deliberate exceptions to "no live code execution" — runs real queries client-side via `sql.js`/WASM (see `src/lib/sqlEngine.js`, a memoized loader shared across instances so the ~700KB engine is fetched once, lazily, only when a playground actually mounts). Each instance owns an isolated, ephemeral database; a "Qayta tiklash" button re-seeds it from `schema`. Used in two places, with different prop shapes: SQL-course lesson bodies pass only `schema`/`initialQuery` — just "Bajarish" (Run), no grading, no `useArenaStore` read at all; `ArenaTopicPage.jsx`'s live sandbox pane for `sql`-topic challenges also passes `challenge`/`topicId`/`slug`, which additionally renders "Yuborish" (Submit) — it re-runs the student's query, runs `challenge.solutionQuery` against a second fresh database, and compares `{ columns, values }` with strict equality; a match calls `useArenaStore.markSolved('sql', slug, query)` (see `docs/agents/auth-and-progress.md`), preloads that saved query next time the challenge is reopened (mirroring `JsPlayground`/`PyPlayground` below), and — if `nextChallenge` was passed — shows a "Keyingi masala" link to it. |
| `JsPlayground` / `PyPlayground` | `challenge` (the full challenge object: `functionName`, `paramNames`, `starterCode`, `examples`, `tests`), `topicId`, `slug`, optional `nextChallenge` | The other two deliberate exceptions to "no live code execution" — LeetCode-style two-button grading, structurally identical between the two (same props, same UI, same `JSON.stringify` deep-equality grading), differing only in which engine actually runs the code. "Yuritish" (Run) executes the student's function against `challenge.examples` only, for quick feedback, and never marks the challenge solved. "Yuborish" (Submit) executes against the full `challenge.tests`; if every case passes it calls `useArenaStore.markSolved(topicId, slug, code)`, which upserts into Supabase's `arena_solved_challenges` (see `docs/agents/auth-and-progress.md`) and preloads that code into the editor next time the challenge is reopened, and — if `nextChallenge` was passed — shows a "Keyingi masala" link to it. `JsPlayground` runs the student's code inside a fresh, disposable Web Worker per run (`src/lib/jsRunner.js` → `src/workers/jsChallengeRunner.worker.js`, `new Function()` under the hood), with a 3s timeout that terminates the worker so an infinite loop can't hang the tab. `PyPlayground` instead runs it through Pyodide (WASM CPython, loaded from a CDN) inside a **persistent** classic Web Worker (`src/lib/pyRunner.js` → `src/workers/pyChallengeRunner.worker.js`) — reused across runs since reloading Pyodide per click would be too slow, with a longer (15s) timeout to cover first-load latency; see `docs/agents/registry-contract.md`'s Arena section for why it's persistent and classic (non-module). Results in both are shown via a "Testlar"/"Natijalar" tab pair with per-test pills (colored green/red once run) and Input/Output/Kutilgan panels below, built from `challenge.paramNames` (falls back to `arg1`, `arg2`, ... if omitted). The editor itself is a small local `CodeEditor` duplicated in each file (not a shared primitive, same as the rest of this pair) — a `prism-react-renderer` `Highlight` overlay (`language="javascript"` / `language="python"`) behind a transparent-text `<textarea>`, giving live syntax highlighting on an editable field; Tab inserts two spaces instead of moving focus. Used only in `ArenaTopicPage.jsx`'s sandbox pane, for `javascript`- and `python`-topic challenges respectively — same dark, theme-independent editor chrome as `SqlPlayground` above. `nextChallenge` (an object with at least `slug`/`title`, or `null`) is computed by `ArenaTopicPage.jsx`, not the playgrounds themselves — see `docs/agents/registry-contract.md`'s Arena section. Don't reuse this pattern for a fourth language without an explicit ask (see AGENTS.md's non-goals). |
| `ChallengeDetail` (`src/components/arena/`) | `challenge`, `topicId`, `schema` | Not a lesson-body primitive (lives in `components/arena/`, not `components/content/`), listed here because it's the counterpart to the three playgrounds above. Dispatches on `topicId`: `sql` renders `SqlChallengeDetail` (computes the expected result table live by running `solutionQuery` against a fresh database, purely for display — the actual grading happens in `SqlPlayground`, not here — plus a "Yechilgan" badge from `useArenaStore.isSolved`); `javascript` and `python` both render `FunctionChallengeDetail` (prompt plus `challenge.examples`, a static input→output list from the challenge file, no engine call, plus the same "Yechilgan" badge — file name predates Python but the component was always topic-agnostic, so it was reused rather than duplicated). Both end with `HintReveal` (`src/components/arena/HintReveal.jsx`, `hint` prop) — a click-to-reveal box (starts collapsed, no attempt-count gating) showing `challenge.hint`, a short prose nudge, deliberately not a full solution; shared across all detail components since the disclosure UI is identical, only the hint string's source field differs. |

The canonical primary-CTA button/link — `rounded-full bg-brand-600 px-{n} py-{n} text-sm font-semibold text-canvas-muted hover:bg-brand-700` — now repeats verbatim across half a dozen files (`HomePage`, `CourseOverviewPage`, `NotFoundPage`, `LoginPage`, `UserMenu`, `Footer`'s brand-icon badge). It has already crossed the old "extract at the third occurrence" threshold below; the working choice so far has been to keep copying the exact class string rather than add a `ui/Button`. When adding a new primary CTA, copy that string exactly rather than approximating it — and if you're the one who finally extracts it into `ui/Button`, that's a real refactor with its own review, not a drive-by while doing something else.

Don't add `ui/Badge` or `ui/IconButton` speculatively — dropped from an earlier draft of this architecture because nothing needed them. Same rule as above: a second occurrence of new shared styling is a coincidence, a third is a pattern worth naming.
