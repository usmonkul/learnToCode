# The registry contracts

Reached from AGENTS.md when changing how content is *discovered* — editing `src/courses/registry.js`, `src/projects/registry.js`, `src/arena/registry.js`, or the shape of `course.meta.js`/`project.meta.js`/`topic.meta.js`. Not needed just to add a lesson, project, or challenge file; the recipes in AGENTS.md cover that.

## Courses (`src/courses/registry.js`)

This is reference material, not something to reimplement — read the file itself before changing content-discovery behavior. The parts that aren't obvious from reading the code once:

- Lesson filenames need a **zero-padded two-digit prefix** (`01-hello-world.jsx`, `02-variables.jsx`, up to `99-`). Ordering is a plain string sort on the glob path, so an unpadded or missing prefix silently breaks ordering.
- A lesson's `slug` is derived from its filename (numeric prefix and `.jsx` stripped) — you never set a slug explicitly.
- `getGroupedLessons` groups only **consecutive** lessons sharing the same `meta.section`. Keep a section's lessons adjacent in the file listing; if you must reorder and a section becomes non-contiguous, the sidebar will just show it as two separate groups with the same heading — not a crash, but confusing for students.
- A lesson missing `export const meta` doesn't crash the app — it falls back to `{ title: slug, section: '' }` and logs a `console.warn`. Still write `meta` explicitly; the fallback exists to keep the failure loud-but-survivable, not as a substitute.
- A course's `id` comes from its folder name, not from anything inside `course.meta.js` — don't add an `id` field there, it would be a second, contradicting source of truth.

Exported API — everything downstream (pages, layout components) reads through this, never through `import.meta.glob` directly: `getAllCourses()`, `getCourse(courseId)`, `getLessons(courseId)`, `getLesson(courseId, slug)`, `getAdjacentLessons(courseId, slug)`, `getGroupedLessons(courseId)`.

## Projects (`src/projects/registry.js`)

"Loyihalar" is the practice-projects gallery at `/loyihalar` — a flat list of small, fully-working project components (in the spirit of 100jsprojects.com), filesystem-driven like courses and Arena. It differs from both in one important way: there's no separate "content" vs. "grading" split — a project's `Project.jsx` *is* the finished, interactive thing a student uses, not prose or a self-check.

- Unlike a course (whose `id` comes from the folder name verbatim) or an Arena challenge (whose `slug` comes from the filename), a project's `id` comes from its **folder name** with the numeric prefix stripped (`01-age-calculator` → `age-calculator`) — same derivation rule as a lesson's slug, just applied to a folder instead of a file, since a project is a folder of exactly two files (`project.meta.js`, `Project.jsx`). That folder name (and therefore the `id`/URL slug) is always English, even though `project.meta.js`'s `title`/`description` are Uzbek — see AGENTS.md's "Language" section.
- Ordering is a plain string sort on the folder's glob path, same zero-padded-prefix rule as lessons and challenges.
- The registry merges `project.meta.js`'s export and `Project.jsx`'s default export into one entry keyed by folder; a `Project.jsx` with no matching `project.meta.js` folder is skipped with a `console.warn` (mirrors the courses/arena "missing piece is loud-but-survivable" pattern) — in practice this shouldn't happen since both files always live in the same folder.
- Exported API: `getAllProjects()`, `getProject(id)`.
- Routing is intentionally asymmetric with courses/Arena: `/loyihalar` (the gallery) renders inside the normal `RootLayout` (TopNav visible), but `/loyihalar/:projectSlug` (an individual project) is a sibling top-level route in `App.jsx`, outside `RootLayout` entirely — no TopNav, no Footer. `ProjectDetailPage` renders `Project.jsx` directly (full page, no imposed container) behind a small fixed-position "back to gallery" link, so opening a project feels like navigating to its own site. Don't move this route back inside `RootLayout` without an explicit ask — that's the whole point of the split.

## Arena (`src/arena/registry.js`)

"Arena" is the practice-challenges area at `/arena` — topics (currently `sql`, `javascript`, `python`) each holding a list of self-checked challenges. It mirrors the courses registry's filesystem-driven design on purpose: same `import.meta.glob` discovery, same zero-padded-prefix ordering rule, same "adding one is one file" principle. Only what differs from the courses contract above is called out here:

- A challenge's `slug` is derived from its filename the same way a lesson's is (numeric prefix and `.js` stripped).
- `topic.meta.js` sets `hasSandbox: true` to opt a topic into rendering a live sandbox next to its challenge list (`ArenaTopicPage.jsx` checks this flag, then branches on `topicId` to pick `SqlPlayground`, `JsPlayground`, or `PyPlayground`) — a topic without a runnable sandbox would omit it or set it `false`.
- `javascript` and `python` challenges share one shape — `functionName`/`paramNames`/`starterCode`/`examples`/`tests`/`hint` — and one detail-view component, `FunctionChallengeDetail.jsx` (renders `prompt` plus `examples`, a static input→output list, no engine call; genuinely topic-agnostic despite the name predating Python, kept because SQL's shape still doesn't fit it). `sql` is the one shape that's actually different — no `tests` array, only `solutionQuery` — and keeps its own `SqlChallengeDetail.jsx`. All three also carry an optional `hint` — a short prose nudge (not code), rendered by `HintReveal` (`src/components/arena/HintReveal.jsx`) at the bottom of whichever detail component is active, collapsed behind a "Maslahat ko'rish" toggle. Deliberately a hint, not a full solution — the challenge files carry no reference implementation for `javascript`/`python` (SQL's `solutionQuery` is the closest thing anywhere, but it's grading infrastructure, not a student-facing answer key — don't wire it into a "show solution" UI without an explicit ask).
- Grading differs per topic, but all three now persist a pass the same way. A `sql` challenge has no stored "expected result" — it ships only `solutionQuery` (plus the optional `hint` above). `SqlChallengeDetail.jsx` computes the expected table live by running `solutionQuery` against a fresh in-memory database on mount, purely for display. `SqlPlayground` grades separately: "Bajarish" (Run) just executes the student's query and shows its output (no grading); "Yuborish" (Submit) executes it, runs `solutionQuery` against another fresh in-memory database, and compares `{ columns, values }` of the two results with strict equality (same column order, same row order — SQL result order isn't guaranteed by the language, but both queries run on the same engine against the same fixture, so it's deterministic in practice for these challenges). `javascript` and `python` challenges are graded LeetCode-style by `JsPlayground`/`PyPlayground` respectively — "Yuritish" (Run) checks the function against `examples` only (quick feedback, never marks solved); "Yuborish" (Submit) checks it against the full `tests` array, `JSON.stringify` deep-equality per case in both. In all three topics, a pass on Submit persists to Supabase via `useArenaStore.markSolved(topicId, slug, code)` — one row in `arena_solved_challenges` per solved challenge, storing the passing `solution_code` (the submitted query or function body) alongside the solve, which the corresponding playground preloads next time that challenge is opened. Don't blur the `sql` shape and the `javascript`/`python` shape together (SQL still has no `tests` array, the other two still have no `solutionQuery`), and don't add a fourth grading style without an explicit ask.
- Python's engine is Pyodide (a WASM CPython build), loaded from jsDelivr's CDN inside a **classic** (non-module) Web Worker — `src/workers/pyChallengeRunner.worker.js`, driven by `src/lib/pyRunner.js` — since `importScripts()` (how Pyodide's own loader script is pulled in) isn't available inside a module worker. Unlike `jsChallengeRunner.worker.js` (a fresh, disposable worker per run), this worker is a **singleton** kept alive across runs by `pyRunner.js`, because reloading Pyodide from the CDN on every "Yuritish"/"Yuborish" click would be far too slow — the CDN fetch + wasm init only happens once per page load (browser HTTP cache thereafter), and each subsequent run gets a fresh Python globals dict so one challenge's state can't leak into the next. `pyRunner.js` correlates requests/responses with a message `id` (the worker can outlive any single call, unlike `jsRunner.js`'s one-shot workers) and applies the same terminate-on-timeout safety net as `jsRunner.js`, just with a longer timeout to accommodate first-load latency — a timeout also nulls out the cached worker, so the next run pays the load cost again, rather than trying to reason about what state an infinite-looping interpreter left behind.
- `ArenaTopicPage.jsx` also computes a `nextChallenge` (first unsolved challenge after the current one, wrapping around the full unfiltered topic list — not the difficulty-filtered subset shown in the sidebar, so it always has somewhere to go) and passes it to whichever playground is mounted. On a passing Submit, all three playgrounds render a "Keyingi masala" link straight to it (or a "hammasi yechildi" message if none remain) so a student can move on without returning to the challenge list. This is presentation-only — it reads `arenaStore.solved` and `getChallenges(topicId)`, it doesn't change grading or persistence.
- Exported API: `getTopics()`, `getTopic(topicId)`, `getChallenges(topicId)`, `getChallenge(topicId, slug)`.
